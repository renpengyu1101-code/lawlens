# LawLens 企业自助上市准备评估发布审查

面向用户已确认的“拟上市企业，自助做上市准备评估”，建议目前先保持受控试用，修复下列结论可靠性和发布安全问题后再开放注册。平台已有材料、版本、证据、任务、报告和复核的基础，但当前评估主线仍是资产、劳动、股权三个领域的材料核查。它还不能独立支持企业判断适用上市路径和资格条件，更不能把评分解释为上市成功概率。[S01][S02]

审查日期：2026-10-28，Asia/Shanghai。来源状态见各项及[来源登记表](来源登记表-发布审查.md)。本轮没有修改应用代码；在独立 probe-data 中使用明确标识的虚构输入进行针对性复现，没有调用外部模型或向运行中的演示库写入测试数据。初始审查源码摘要见 [source-hashes.json](source-hashes.json)，独立复校时摘要见 [current-source-hashes.json](current-source-hashes.json)（main.py 在审查期间变化，已按当前源码修正相关结论；不推断修改者），可复现输入与结果见 [probe_logic.py](probe_logic.py)、[probe-results.json](probe-results.json)。本次没有重跑全量回归、并发压测或真实企业材料验证，不能沿用此前版本的通过项数作为当前发布证明。[S12]

## 发布前应解决的问题

下述优先级是本次审查建议，不是外部评级。P0 表示影响核心结论或公网安全；P1 表示发布前需要修复的流程和一致性问题。

### P0 上市资格评估尚未形成完整计算流程

【有来源】`execute_pipeline` 固定跑三个法律核查维度；港股专项 `check_hk_missing` 只用关键词判断材料是否存在，没有利润、市值、收入、现金流的结构化计算，也没有按企业类型选择上市路径。`build_task_spec` 把用户问题记录为 objective，但核查项仍取固定清单。不能因为用户输入“上市可能性”就认为系统实际进行了上市资格评估。[S01]

建议把产品结果分为：适用路径、已验证条件、尚缺条件、不可判断事项、整改行动。首版可明确只支持经核实的主板一般企业路径；特殊路径显示“不在本版本评估范围”，待规则验证后逐步增加。港交所官方页面列出的主板财务资格包含不同测试路径，业务规则应逐条实现并保留版本。[S10]

### P0 评分把部分未知情况转成了满分

【有来源】评分只使用项目级 analyzed；只要该值为真，某核查代码没有风险命中就给该项满分，没有核查项级的完成证据。在构造的 `board=all`、空 findings、存在缺料的测试输入中，资产、劳动、股权分别获得20、20、25分。实际流水线又允许缺料维度跳过，因此这个接口设计不能区分“未核查”和“已核查无异常”。此外，权重合计为95，声明总分却为100。[S02]

【有来源】外部评分只判断有无 external_checks 记录。从调用方记录判定与评分代码可推知：搜索渠道返回而工商渠道未返回时，D1 仍可获5分；探针仅构造 external_present=true 验证该评分分支，未实调搜索或工商服务。未核实搜索线索还可直接扣分。不能把“没有查到负面结果”解释为主体登记正常或不存在重大风险。[S02]

建议先停用面向企业的总体等级，保留可核实的逐项状态。核查项至少区分“未评估、待补料、待确认、满足、不满足、不适用”，只有完成证据核对的项目进入评分。评分权重和扣分参数应作为产品方法论明确披露；缺少结果样本校准时，不展示成功概率。

### P0 规则中存在确定性的错误判断

【有来源】AST-04 将“出租方名称不同于拟上市主体”作为“出租方非产权人”的触发条件。虚构测试中，租户乙向房东甲租赁也触发该结论。代码比较的是出租方与租户，不是出租方与该物业登记权利人，现有输入不足以推出无权出租。[S04]

建议先建立主体、子公司、资产、出租人、登记权利人、合同及日期的关联，再判断是否一致。不同资产的权利人不同也不应直接作为字段冲突。每条规则都需要正常、异常、缺证及例外样本，经专业人员确认后启用；把固定案例测试当成规则验证是不够的。

### P0 证据定位和材料完整性不能保证当前结论

【有来源】质检在全文中寻找 quote，不检查其是否出现在所标页码；虚构样例把第一页引文标为999页，仍通过。DOCX 解析统一写为第1页；包含显式分页符的测试文件仍返回1页。PDF 的文字判断把页码标记残留算入文本长度，10页空白测试 PDF 被标为 parsed。[S05][S06]

【有来源】文件名含必需材料关键词、正文为空的样例通过缺料检查。模型抽取只取正文前12000字符，尾部样例信息没有进入模型请求；模型异常可退回规则抽取而没有持久记录降级原因，抽取 confidence 固定为0.9。[S05]

建议保存原文件、文档版本、页或段落位置和原文跨度；DOCX 没有可靠物理页码时应显示段落/表格位置，或在固定渲染版本上定位。先验证解析覆盖与可读性，再判断材料齐全。长文分块覆盖全部材料，记录未处理页和降级状态；未知不得伪装成已完成。

### P1 材料更新没有使旧结论和旧复核失效

【有来源】已完成项目追加材料后仍保持 done，隔离接口测试已复现。新版本接口在项目 running 时仍接受请求。citations 只关联 document_id，而上传版本会改写同一 documents 行；旧 findings 与 review 没有绑定不可变材料快照。管理员可把含阻断触发项的待复核单直接批准为 done，当前接口不要求补证或逐项处理。[S07]

建议每次核查生成独立 assessment_run，绑定材料版本、规则版本、模型配置、评估时点和复核人。更新材料后明确显示“旧报告基于旧材料，需重新评估”，而不是继续展示成当前完成结果。自动校验失败不允许简单点“通过”；如人工推翻机器结果，需要补入依据和变更记录。正式报告应由已签署的评估快照生成。

### P1 三维度改造与旧汇总逻辑没有对齐

【有来源】新工作台创建 `board=all`，但主体汇总只取 asset/labor/equity，`all` 项目的前三维显示 N/A；虚构测试已复现。旧板块存在多个项目时，代码按id升序配合 setdefault，实际取最早项目。评分所需材料也从没有 all 键的 BOARD_REQUIRED 获取。[S03]

【有来源】合并质检 merged_qc 缺少 checked 和 issues；报告使用 checked 的默认值0。项目详情及评分只读最后一条 qc_runs，不能代表整轮多维核查。重新执行的 task_runs 没有轮次标识，进度接口读全部历史步骤。[S03]

建议统一围绕同一次评估快照展示项目详情、主体汇总、评分、质检和报告；避免各处自行取“最后一条记录”。同一企业重跑时要能看到本轮与上轮的变化。

### P0 模型接入和账号机制不能直接照搬到公网

【有来源】模型 base 可由普通已登录用户传入；后端直接向该地址发请求，且 key 可回退到服务端环境变量。若部署使用平台统一密钥，这条路径可能把平台密钥发往用户指定地址，并产生服务器访问不受控地址的风险。这是代码可达性判断，本次没有进行真实外发或内网探测。[S08]

【有来源】改密码仅更新哈希，不撤销旧会话；隔离测试中的旧 cookie 在改密后仍可访问。当前代码已支持通过 DILIGENCE_COOKIE_SECURE 配置 Secure cookie（默认关闭），实际生产启用情况【待补】；默认签名密钥只警告、不阻止启动。当前生产代理、防火墙、HTTPS和限流配置【待补】，需在目标部署环境核验。[S08]

建议由平台管理允许的模型服务端点和密钥，限制出站网络；企业用户无需自行填写模型 Key。上线环境强制安全配置、HTTPS、会话撤销、认证限流、企业与项目权限。材料传往外部模型的处理方式、留存和删除安排应在上传前说明，并由专业人员确认适用的数据合规要求。

### P1 企业自助入口需要先明确主体和评估阶段

【有来源】工作台仍允许不填主体，所有新项目硬编码 is_demo=true，真实企业材料可能生成“虚构测试样本”报告。创建、上传、启动任务分成多个请求，失败后没有复用既有项目的恢复流程；未附文件仍先建项目再收到启动失败。积分先扣，全部维度缺料时直接 return，没有在该分支退还。[S09]

建议先保存企业档案和草稿，再做免费材料预检及范围确认；明确本次将评估什么、哪些还不能评估，再进入付费或扣积分步骤。失败后回到原项目补料或继续。真实企业项目与演示样本必须分开。

### P1 规则版本与法律依据需进入产品治理

【有来源】三个业务规则库仍为 rule_ref=null。内置上市规则检索是额外的条文关联，不能替代每项判断的适用依据。条文记录/检索输出主要是条号、板块、页码和文本，没有在该结果中携带生效期与原件链接。`HK_REQUIRED` 仍将公众持股写为通用25%门槛；港交所2025年改革已对初始公众持股采用区分情形的安排，不能将25%写成通用条件。[S10]

建议规则记录至少包含原件链接、适用范围、生效及失效日期、核验人、规则版本和例外。把上市资格、内地经营合规、信息披露分别建模；不能仅给所有风险挂“适合上市”条文就当作完整法律论证。

### P1 任务与文件生命周期要经发布环境验证

【有来源】任务用 FastAPI 进程内 BackgroundTasks；启动恢复把所有 running 项目标失败并退款。扩展为多进程时，需防止新工作进程把其他进程的活跃任务误判为中断。版本上传没有与普通上传相同的 MAX_UPLOAD_MB 检查；删除项目只遍历当前 documents 和 reports 的路径，历史版本文件可能留在磁盘。此项为静态审查，未做并发和删除压力测试。[S11]

建议为每次任务保存唯一编号、幂等键、心跳、重试状态和计费流水；按验证过的规模决定何时引入独立任务队列、PostgreSQL和对象存储。补齐上传配额、解析资源限制、备份恢复演练、历史版本删除清单和监控。SQLite 本身不是发布结论，关键是业务状态一致性与可恢复性。

## 建议的企业自助流程

以下是产品设计建议，不是现有功能事实。

1. 企业建档：法定名称、唯一标识、注册地、集团关系、行业和拟上市阶段；区分“本企业”与关联公司。
2. 选择评估范围：先展示本版本支持的上市路径，让企业确认适用范围；不支持的路径说明原因。
3. 填写关键事实：财务年度、币种、经审计数据、发行方案等；自动抽取只作为待确认输入，关键数字由企业确认并附证据。
4. 动态材料清单：依据行业、资产、用工及融资情况要求材料；允许有证据的“不适用”，不能强迫所有企业提供争议文书或派遣协议。
5. 免费预检：提示哪些文件不可读、缺页、过期、对象不匹配；展示真实覆盖范围和下一步费用。
6. 逐项评估：资格条件分别计算，重大风险分别判定，证据不足单独列示；禁止用其他高分抵消关键条件不满足。
7. 结果页：适用路径、已验证条件、缺口、待核实项、证据和整改建议；以行动为主，分数为辅。
8. 补料与复评：每项缺口连接到上传入口、责任人和状态；展示新增材料后哪些结论改变，保留旧版快照。
9. 专业复核：普通企业用户可获取明确标注的自动初评；高风险、关键条件和正式对外报告进入有身份与责任边界的专业复核，不由普通管理员角色代替专业资格。

## 实施顺序与验收

| 阶段 | 建议范围 | 完成标准 |
|---|---|---|
| 先修结论可靠性 | 缺项满分、出租方比较、解析及定位、all汇总、旧结论失效 | 本次反例全部有明确的期望行为和回归测试；不同页面/报告引用同一评估快照 |
| 再完成产品主线 | 企业建档、动态清单、一个明确受支持的上市路径、条件与整改清单 | 缺证能停在“待补”；关键条件不满足不会被总分掩盖；真实项目不带虚构样本标记 |
| 然后受控试用 | 经授权且处理合适的真实案例、专业人员参考判断、用户完成度反馈 | 分别记录误报、漏报、未覆盖和人工改判原因；不编造准确率或完成时间 |
| 最后公开发布 | 端点及密钥、认证权限、任务一致性、数据生命周期、恢复和监控 | 目标部署环境验证通过；隐私与服务边界已审核；回归、容量和恢复演练有记录 |

【待补】真实案例准确性、行业覆盖、性能容量、费用成本、规则全量时效、目标部署安全与数据合规。下一步分别通过授权样本对照复核、规则矩阵核验、压测与恢复演练、模型计量和部署审查补齐；不填写估计值替代实测。

本报告结论为发布准备建议，不是对任何企业是否符合上市条件的法律意见。
